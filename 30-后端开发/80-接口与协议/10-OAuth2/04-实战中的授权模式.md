# 实战中的授权模式

> 对应书中 **第 3 章 3.1（授权码授权模式的应用）**，当前覆盖到 **3.1.1 获取 code**。
>
> 一句话：第 1 章讲“流程长什么样”，第 3 章讲“**真做起来要处理什么**”——把“拿 code”拆成 3 步，难点全在**用户登录怎么接、参数存哪、code 怎么生成**。

## 零、本章要讲什么

实践中会用到授权码、授信客户端密码、授信客户端三类模式，并在此基础上演变出两种变种：

| 模式 | 一句话 | 本篇状态 |
| --- | --- | --- |
| **授权码授权** | 最广泛、最安全，实战细节最多 | 本篇 3.1.1（进行中） |
| **授信客户端密码** | 应用拿用户账号密码换令牌 | 后续小节 |
| **授信客户端** | 应用用自己的凭证换令牌 | 后续小节 |
| **用户名密码授权码模式**（变种） | 用户名密码 + 授权码的组合 | 后续小节 |
| **插件化授权模式**（变种） | 在服务市场/客户端内直接完成授权 | 后续小节 |

## 一、为什么还要再讲一遍授权码模式

授权码模式的**流程与优势**已经在第 1 章讲完（见 [[30-后端开发/80-接口与协议/10-OAuth2/02-OAuth 2 的四种授权模式|02-OAuth 2 的四种授权模式]]），这里不再重复，只讨论**落地实现**，分三块：

1. **获取 code**（本篇）
2. 获取授权信息
3. 刷新授权信息

## 二、步骤 1：发起授权请求（对应图 1-2 的第 1、2 步）

用户先访问第三方应用，再由应用把浏览器引导到授权地址——可以直接访问网址，也可以从页面点超链接跳转。请求如示例 3.1：

```http
GET https://example.oauth.com/oauth2/authorize
  ?client_id=##
  &response_type=code
  &redirect_url=##
  &state=##
  &scope=##
```

*示例 3.1 授权码请求*

| 参数 | 含义 |
| --- | --- |
| `client_id` | 第三方应用在控制台注册后拿到的唯一标识 |
| `response_type` | 授权码模式固定为 `code` |
| `redirect_url` | 回调地址，必须与注册值一致 |
| `state` | 应用自定义，回调时原样带回，用于校验 / 幂等 |
| `scope` | 申请的权限列表，逗号分隔 |

> 书中因排版把 `oauth2` 显示成 “OAuth 2”、把 `client_id` 显示成 “client id”；本笔记统一写作 `oauth2` / `client_id`，与 02 篇保持一致。

### 授权系统收到请求后做三件事

1. **校验 `client_id`**：应用是否存在；
2. **校验 `redirect_url`**：是否与控制台登记的一致（防回调被劫持）；
3. **校验 IP 地址白名单**：来源是否在控制台配置的白名单内。

三项都通过后，才开始处理权限：

```text
请求的 scope 列表
    │ ① 去掉“第三方应用还没开通”的权限
    │ ② 去掉“无效”的权限
    ▼
过滤后的权限列表 → 展示给用户，让用户明确自己要授权哪些范围
```

> 关键：**展示给用户的权限，不等于请求里带的 scope**。这与 03 篇讲的“scope 与权限包取交集”是同一套逻辑——申请归申请，能授多少由平台已批准的范围决定。

**这一步的数据从哪来？** `client_id`、回调地址、IP 白名单都存在 [[30-后端开发/80-接口与协议/10-OAuth2/03-开放平台整体架构|03-开放平台整体架构]] 里讲的控制台系统中。

## 三、步骤 2：让用户登录并授权（对应图 1-2 的第 3、4 步）

这是实战中最麻烦的一步：**授权系统和登录系统往往不是同一个**，还要在登录页上把“谁在向你要什么权限”讲清楚。

书中给了两种实现方式。

### 方式一：授权系统自己做登录

**做法**：授权系统收到示例 3.1 的请求后，把请求参数和授权提示信息放进**请求域**，用 **forward**（服务端转发，不是 302 重定向）转到自己的登录页。用户登录成功后，因为仍在同一个系统里，**不需要图 1-2 的第 4 步**，直接拿用户信息继续下一步。

**优点**：实现简单，不依赖外部系统。

**缺点**：

- 做一个**可用的、安全**的登录系统并不简单——要防脚本攻击、要保存维护用户信息、要多端适配，成本很高；
- 大公司通常有**专门团队**维护统一登录认证系统，全公司都对接它。自己再写一套，既是重复造轮子，又要额外兼容已有账号体系。

**什么时候选它**：小团队、没有统一登录体系、或授权系统本身就带账号体系。

> `forward` 与 `redirect` 的区别：forward 是**服务端内部转发**，浏览器地址不变，请求域里的参数还在；redirect 是**让浏览器重新发一次请求**，参数得靠 URL 或 session 传递。这里选 forward 正是为了保留请求参数。

### 方式二：交给登录系统（大型组织的做法）

**做法**：授权系统只负责“准备好上下文”，登录交给协作部门的登录系统。全过程三步。

#### 1）持久化参数

授权系统要在用户登录回来后**还能拿到原来的请求参数**（才能据此生成 code），所以先把参数存起来。方案很多，书中以 Redis 为例：

- 生成一个 **UUID 作为 key**；
- 把参数转成 **JSON 作为 value**；
- 存进 Redis，并**设置过期时间**（一般 5 分钟）。

```text
key: 58af2482-45c4-47b7-9080-fed2ac868627
value:
{
  "client_id": "7c6bdb6a3f1049b893a4a6294e241110",
  "redirect_url": "https://www.example.com",
  "response_type": "code",
  "scope": "base_info,shop_operate",
  "state": "my_sate"
}
```

*示例 3.2 授权参数持久化*

**为什么要设 5 分钟过期**：用户 5 分钟内没登录完，就让他**从头再来**。这样授权系统不用做复杂的缓存清理，Redis 里也不会堆一堆垃圾数据。

> 书中示例里的 JSON 用的是全角引号与冒号（排版导致），实际代码里必须是半角。`state` 的值原文写作 `my_sate`，按原样保留。

#### 2）发送请求到登录系统

登录系统需要**专门为授权系统定制**一个登录场景，原因有两个：

- 登录页要向用户展示**权限列表**和**第三方应用信息**；
- 用户完成授权后，要把请求**重定向回授权系统**。

引导登录的请求如示例 3.3：

```http
GET https://passport.oauth.com/oauth2/login
  ?nls=##
  &redirect_url=https%3A%2F%2Fexample.oauth.com%2Foauth2%2Fcode%3FsessionToken%3Duuid
  &client_name=##
  &client_img=##
  &signature=##
  &terms=##,##,##
```

*示例 3.3 引导用户登录请求*

| 参数 | 含义 |
| --- | --- |
| `nls` | 控制跳转后**是否强制登录**：`1` = 即使已有登录态，也要用户点一次“登录”按钮；`0` = 有登录态就直接继续。作用之一是**方便用户换账号** |
| `redirect_url` | 登录成功后的回调地址，值是 `https://example.oauth.com/oauth2/code?sessionToken=uuid` 经 **URLEncode** 后的结果。其中 `sessionToken` 就是示例 3.2 里那个 UUID key |
| `client_name` | 第三方应用注册时设置的应用名称，用于页面展示 |
| `client_img` | 第三方应用注册时设置的应用图标，用于页面展示 |
| `signature` | 所有参数**自然排序**后的签名，供登录系统验签 |
| `terms` | 最终展示给用户的授权范围列表 |

**`terms` 怎么来的：**

```text
第三方应用已拥有的权限列表  ∩  请求的 scope 列表  =  terms
```

在登录页上，正是靠 `client_img` + `client_name` + `terms` 三样东西，明确告诉用户：**谁**要**哪些权限**。如图 3-1 所示。

#### 3）回调授权系统

用户登录成功后：

1. 登录系统先在**浏览器 cookie** 里写入用户登录态；
2. 再按 `redirect_url` 回调授权系统（其中带着 `sessionToken`）；
3. 授权系统**对接了登录系统的拦截器**，所以收到回调时既能拿到**用户登录态**，也能用 `sessionToken` 取出**缓存的第三方应用信息**；
4. 两者齐了，就可以进入下一步（生成 code）。

> [!important] `sessionToken` 只能用一次
> 一般取完缓存信息就**立刻删除**该 key。这样即使 token 被截获，也无法重放，安全性更高。

### 两种方式怎么选

| 维度 | 方式一：自己登录 | 方式二：交给登录系统 |
| --- | --- | --- |
| 依赖 | 无 | 依赖协作部门的登录系统（需定制开发） |
| 开发成本 | 自建一整套安全登录 | 只做持久化 + 跳转 + 回调 |
| 账号体系 | 要自己维护、可能与公司账号不兼容 | 直接复用公司统一账号 |
| 图 1-2 的第 4 步 | 不需要（同系统） | 需要（跨系统回调） |
| 适合 | 小团队、独立产品 | 大型组织、统一登录 |

## 四、步骤 3：生成 code 并回调（对应图 1-2 的第 5 步）

此时授权系统已经拿到用户信息，接下来：

1. **生成随机的 `code`**；
2. 把**用户信息**和示例 3.2 里的参数合并，仍以 key-value 形式写入 Redis，**过期时间同样 5 分钟**；
3. 这里的 **key 就是 `code`**。

```text
key: <生成的 code>
value:
{
  "client_id": "7c6bdb6a3f1049b893a4a6294e241110",
  "redirect_url": "https://www.example.com",
  "response_type": "code",
  "scope": "base_info,shop_operate",
  "state": "my_sate",
  "pin": "fake_pin",
  "shop_id": "fake_shop"
}
```

*示例 3.4 code 缓存信息*

**与示例 3.2 的差异**：多了 `pin` 与 `shop_id` 两项**用户信息**。它们是为下一步换取 `access_token` 准备的——第三方拿 code 来换令牌时，授权系统要能知道“这是**谁**的授权”。

最后，授权系统拼出回调地址并**重定向到第三方应用**：

```http
https://example.com/callback?state=##&code=##
```

*示例 3.5 携带 code 的回调*

| 参数 | 含义 |
| --- | --- |
| `state` | 步骤 1 传进来的值，**原样回传**，第三方据此校验回调真伪 |
| `code` | 一次性授权码，第三方拿它去后端换 `access_token` |

> `code` 的格式有很多种，书中后续会专门讨论；现在只要记住：**code 本身不是令牌，它只是一把“取货凭证”**，真正的授权信息存在服务端缓存里。

## 五、实战要点

- **三处缓存，都是一次性或短命**：`sessionToken` 用完即删；`code` 5 分钟过期；换完令牌后 code 也应该作废。
- **`redirect_url` 必须与控制台登记值一致**，且传给登录系统前要 **URLEncode**——少编码一层，回调就会丢参数。
- **`terms` 是交集，不是原始 scope**：用户看到的权限一定 ≤ 应用被批准的权限。
- **`state` 全程原样带回**：这是防 CSRF / 防伪造回调的基本手段。
- **`nls` 决定“要不要多点一次登录”**：`1` 方便换账号，`0` 方便静默续接登录态。
- **key 用 UUID、code 用随机串**：都不可预测，避免被枚举。
- **两种登录方式的根本差别是“第 4 步要不要”**：同系统用 forward 省掉回调；跨系统必须有一次回调。

## 六、专有名词与缩写

| 术语 | 全称 / 含义 | 在本篇的作用 |
| --- | --- | --- |
| **code** | Authorization Code，授权码 | 一次性凭证，第三方用它换 `access_token` |
| **sessionToken** | 会话令牌 | 登录回调时携带的 UUID，对应授权参数缓存的 key |
| **UUID** | Universally Unique Identifier | 用做缓存 key，保证唯一且不可猜测 |
| **TTL** | Time To Live | 缓存存活时间，示例中为 5 分钟 |
| **Redis** | 内存键值数据库 | 存放授权参数与 code 的缓存 |
| **forward** | 服务端转发 | 内部跳转登录页，保留请求域参数 |
| **redirect** | 重定向 | 让浏览器重新发起请求，参数靠 URL / session 传递 |
| **请求域** | request scope | 一次请求内的参数容器，forward 时仍可访问 |
| **URLEncode** | 百分号编码 | 把回调地址作为参数值传输前必须编码 |
| **签名（signature）** | — | 参数自然排序后生成，供对方验签防篡改 |
| **nls** | 书中未给全称 | 控制登录页是否强制用户点“登录” |
| **pin / shop_id** | 业务侧用户标识 | 示例中代表“用户信息”，换令牌时要用 |
| **登录态** | — | 存在浏览器 cookie 里的用户登录凭证 |
| **拦截器** | Interceptor | 授权系统借此在回调时读取登录态 |
| **权限包 / scope** | — | 见 [[30-后端开发/80-接口与协议/10-OAuth2/03-开放平台整体架构|03-开放平台整体架构]] |
| **access_token** | 访问令牌 | code 换来的最终凭证 |
