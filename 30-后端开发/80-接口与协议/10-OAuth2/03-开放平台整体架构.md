# 开放平台整体架构

> 对应书中 **第 2 章（2.1 功能架构）**。一句话：开放平台 = **外部系统** + **内部系统**；外部负责对接第三方应用，内部负责管理审批与能力开放；三座网关（API / SPI / 消息）负责打通里外，再配上一组支撑系统（授权、控制台、门户、HUB、CMS、MAN、加解密、登录认证）。缩写含义见文末“**专有名词与缩写**”。

## 一、先看全局：外部系统 vs 内部系统

从对用户服务的角度，开放平台可分为**外部系统**与**内部系统**，如图 2-1 所示。

![[图2-1开放平台架构.excalidraw]]

*图 2-1 开放平台整体架构*

| 分层 | 面向谁 | 作用 |
| --- | --- | --- |
| **外部系统** | 第三方应用开发者 | 开发者通过对接外部系统，把 Web / H5 / 移动 App 等应用与开放平台连接起来 |
| **内部系统** | 平台内部 | ① 负责管理与审批；② 支持内部应用对外开放自身能力 |

其中，**内部应用**会通过四种方式把能力交给开放平台：

- RPC 接口
- REST 接口
- MQ 消息
- 外部回调

> 记忆：**外部进得来、内部出得去**——第三方通过网关调内部能力，内部也能反向调第三方。

## 二、三座网关（最容易混，先横向对比）

| 网关 | 方向 | 一句话 |
| --- | --- | --- |
| **API 网关** | 第三方应用 → 内部应用 | 第三方访问开放 API 的入口 |
| **SPI 网关** | 内部应用 → 第三方应用 | 内部反向调用第三方接口 |
| **消息网关** | 内部应用 → 第三方应用 | 以统一格式发送消息 / 事件通知 |

### 1. API 网关：外部调内部

- **定位**：第三方应用访问开放平台中开放 API 的入口。
- **API 从哪来**：内部应用通过 **HUB 系统**，把内部的 RPC / REST 接口发布到 API 网关。
- **第三方完整链路**：

  1. 在**控制台系统**创建应用，申请 API 权限（一般包装成**权限包**）；
  2. 引导用户进行授权；
  3. 通过**授权系统**获取用户授权信息（token）；
  4. 用 HttpClient 或开放平台 SDK 请求 API 网关；
  5. API 网关根据 token 做权限校验；
  6. 校验通过后，网关把协议转换成内部应用可识别的 RPC / REST 调用；
  7. 执行请求并返回结果。

### 2. SPI 网关：内部调外部

- **定位**：与 API 网关方向相反——让内部应用能够调用第三方应用的接口。
- **流程**：

  1. 内部用户在 **HUB 系统**中定义一套协议标准（方法名、入参、出参等）；
  2. 第三方应用按该标准实现 REST 接口，并通过**控制台系统**把接口绑定到对应协议标准下（需要具备"实现该标准"的权限）；
  3. 内部应用通过 **SPI 网关**指定 `client_id`（第三方应用在开放平台注册后的唯一标识）调用第三方。

### 3. 消息网关：内部发消息给外部

- **定位**：提供格式统一的"内部应用 → 第三方应用"消息能力。
- **流程**：

  1. 内部应用在 **HUB 系统**申请队列权限与消息类型 `tag`；
  2. 拿到队列和 `tag` 后，按标准向队列发送消息；
  3. 消息字段固定为：`msg_id`（消息 ID）、`tag`（消息类型）、`data`（消息体）；
  4. 第三方应用在**控制台**申请订阅，并把接收消息的 REST 接口绑定到订阅上；
  5. 第三方按约定格式返回结果（书中以"购买成功 / 失败"为例）。

> **SPI 网关 vs 消息网关**：都是内部调外部。SPI 是**同步调用接口**；消息网关是**异步消息 / 事件**。

## 三、支撑系统一览

| 系统 | 作用 | 记忆点 |
| --- | --- | --- |
| **服务市场** | 第三方应用开发者开发的应用的**售卖环境** | 对接完成后申请上架，用户即可购买 |
| **授权系统** | 用户获取系统**访问凭证**的入口 | 本书重点 |
| **控制台系统** | 第三方开发者申请、管理应用 | 开发者的"**个人工作台**" |
| **门户系统** | 介绍系统、提供对接文档 | 开发者**学习与查文档**的地方 |
| **HUB 系统** | 内部应用对接开放平台的主要系统 | 发布 API、定义 SPI、发布 MQ |
| **CMS 系统** | 内容管理系统 | 管理**门户系统**中的文章 |
| **MAN 系统** | 供开放平台**运营人员**使用 | 审核 HUB 内部用户的申请 + 平台管理 |
| **加解密系统** | 内外信息加解密 | 内部走 RPC，外部通过 API 网关 |
| **用户登录认证系统** | 用户登录认证 | **图 2-1 未画**：通常由专职部门开发管理，平台只需对接 |

> 关于"用户登录认证系统"：它一般由专职部门负责开发与管理，开放平台只做对接，因此图中没有画出来。这并不是强制标准——如果开放平台自己实现了登录认证模块，它应当出现在外部系统中。

## 四、把流程串起来

### 场景 A：第三方调用平台能力

```text
第三方应用
  │ ① 控制台创建应用、申请权限包
  ▼
控制台系统 ──▶ 授权系统 ──▶ 用户授权
  │                           │
  │ ② 拿到 token              │
  ▼                           ▼
HttpClient / SDK ───────▶ API 网关 ──校验 token──▶ 内部应用（RPC / REST）
                                                        │
                         ◀────────── 返回结果 ───────────┘
```

### 场景 B：平台反向调用第三方

```text
内部应用 ──▶ SPI 网关 ──指定 client_id──▶ 第三方应用（按 HUB 定义的协议实现 REST）
内部应用 ──▶ 消息网关 ──msg_id / tag / data──▶ 第三方应用（订阅队列，绑定 REST 接收）
```

## 五、易混点小抄

- **API 网关 vs SPI 网关**：方向相反。API 是"外部调内部"，SPI 是"内部调外部"。
- **SPI 网关 vs 消息网关**：都用于内部调外部；前者同步调接口，后者异步发消息。
- **HUB 系统是内部应用的统一入口**：发布 API、定义 SPI、发布 MQ 都在这里。
- **控制台 vs MAN**：控制台给**第三方开发者**用；MAN 给**平台运营人员**用。
- **门户 vs CMS**：门户是给人看的文档站；CMS 是管理门户文章的后台。
- **加解密系统是"内外通吃"**：内部走 RPC，外部通过 API 网关暴露。
- **图里没有登录认证系统 ≠ 不需要**：它通常由专职部门提供，平台负责对接。

## 六、专有名词与缩写

| 缩写 / 术语          | 英文全称                                 | 中文含义                | 在本笔记中的作用                           |
| ---------------- | ------------------------------------ | ------------------- | ---------------------------------- |
| **API**          | Application Programming Interface    | 应用程序编程接口            | 系统对外提供的可调用接口；这里指开放平台开放给第三方的接口      |
| **SPI**          | Service Provider Interface           | 服务提供者接口             | 与 API 方向相反：内部定义协议标准，由第三方实现接口，供内部调用 |
| **SDK**          | Software Development Kit             | 软件开发工具包             | 平台提供的客户端工具包，封装调用 API 的鉴权、请求等细节     |
| **RPC**          | Remote Procedure Call                | 远程过程调用              | 像调本地方法一样调用远程服务；内部应用之间常用            |
| **REST**         | Representational State Transfer      | 表述性状态转移             | 基于 HTTP 的资源式接口风格                   |
| **MQ**           | Message Queue                        | 消息队列                | 异步消息中间件；消息网关借此传递消息                 |
| **HTTP / HTTPS** | HyperText Transfer Protocol / Secure | 超文本传输协议（HTTPS 为加密版） | Web 通信协议                           |
| **H5**           | HTML5                                | —                   | 基于 HTML5 的移动端网页应用                  |
| **token**        | —                                    | 令牌                  | 用户授权的凭证；API 网关据此做权限校验              |
| **client_id**    | —                                    | 客户端标识               | 第三方应用在开放平台注册后的唯一标识                 |
| **msg_id**       | —                                    | 消息 ID               | 消息网关中标识一条消息                        |
| **tag**          | —                                    | 消息类型标签              | 消息网关中标识消息类型                        |
| **data**         | —                                    | 消息体                 | 消息网关中承载的具体内容                       |
| **HUB**          | —                                    | 内部应用对接系统            | 发布 API、定义 SPI、发布 MQ 的系统            |
| **CMS**          | Content Management System            | 内容管理系统              | 管理门户系统中的文章                         |
| **MAN**          | —（书中系统名）                             | 运营管理系统              | 供平台运营人员审核申请与管理                     |
| **HttpClient**   | —                                    | HTTP 客户端            | 代码中用于发起 HTTP 请求的客户端组件              |

补充概念：

- **权限包**：把一组 API 权限打包，第三方应用申请、平台审核后获得；通常与 scope 对应。
- **Web / App**：Web 指浏览器端网页应用；App 指移动端应用。
- **开放平台 / 第三方应用**：见 [[30-后端开发/80-接口与协议/10-OAuth2/01-OAuth 2 的定义与核心角色|01-OAuth 2 的定义与核心角色]]。

> 易混：**API** 是“别人调我”（对外提供），**SPI** 是“我调别人”（对外要求实现）。在开放平台里，API 网关负责前者的入口，SPI 网关负责后者的出口。
