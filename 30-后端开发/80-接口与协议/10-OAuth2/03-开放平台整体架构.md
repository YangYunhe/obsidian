# 开放平台整体架构

> 对应书中 **第 2 章（2.1–2.4）**。一句话：开放平台 = **外部系统** + **内部系统**；外部负责对接第三方应用，内部负责管理审批与能力开放；三座网关（API / SPI / 消息）负责打通里外，再配上一组支撑系统（授权、控制台、门户、HUB、CMS、MAN、加解密、登录认证）。
>
> 四节分工：**2.1** 讲有哪些系统（全景）；**2.2** 讲 API 网关怎么实现、怎么鉴权；**2.3** 讲控制台给开发者做什么；**2.4** 讲售卖型应用与服务市场。缩写含义见文末“**专有名词与缩写**”。

## 一、先看全局：外部系统 vs 内部系统

从对用户服务的角度，开放平台可分为**外部系统**与**内部系统**，如图 2-1 所示。

![[图2-1开放平台架构.excalidraw]]

*图 2-1 开放平台整体架构*

| 分层 | 面向谁 | 作用 |
| --- | --- | --- |
| **外部系统** | 第三方应用开发者 | 开发者通过对接外部系统，把 Web / H5 / 移动 App 等应用与开放平台连接起来 |
| **内部系统** | 平台内部 | ① 负责管理与审批；② 支持内部应用对外开放自身能力 |

其中，**内部应用**会通过四种方式把能力交给开放平台：

- RPC 接口
- REST 接口
- MQ 消息
- 外部回调

> 记忆：**外部进得来、内部出得去**——第三方通过网关调内部能力，内部也能反向调第三方。

## 二、三座网关（最容易混，先横向对比）

| 网关 | 方向 | 一句话 |
| --- | --- | --- |
| **API 网关** | 第三方应用 → 内部应用 | 第三方访问开放 API 的入口 |
| **SPI 网关** | 内部应用 → 第三方应用 | 内部反向调用第三方接口 |
| **消息网关** | 内部应用 → 第三方应用 | 以统一格式发送消息 / 事件通知 |

### 1. API 网关：外部调内部

- **定位**：第三方应用访问开放平台中开放 API 的入口。
- **API 从哪来**：内部应用通过 **HUB 系统**，把内部的 RPC / REST 接口发布到 API 网关。
- **第三方完整链路**：

  1. 在**控制台系统**创建应用，申请 API 权限（一般包装成**权限包**）；
  2. 引导用户进行授权；
  3. 通过**授权系统**获取用户授权信息（token）；
  4. 用 HttpClient 或开放平台 SDK 请求 API 网关；
  5. API 网关根据 token 做权限校验；
  6. 校验通过后，网关把协议转换成内部应用可识别的 RPC / REST 调用；
  7. 执行请求并返回结果。

上面这 7 步只回答了“谁调谁”。网关**内部**怎么分层实现、拿到 `access_token` 后具体怎么鉴权，见 **第五节**。

### 2. SPI 网关：内部调外部

- **定位**：与 API 网关方向相反——让内部应用能够调用第三方应用的接口。
- **流程**：

  1. 内部用户在 **HUB 系统**中定义一套协议标准（方法名、入参、出参等）；
  2. 第三方应用按该标准实现 REST 接口，并通过**控制台系统**把接口绑定到对应协议标准下（需要具备"实现该标准"的权限）；
  3. 内部应用通过 **SPI 网关**指定 `client_id`（第三方应用在开放平台注册后的唯一标识）调用第三方。

### 3. 消息网关：内部发消息给外部

- **定位**：提供格式统一的"内部应用 → 第三方应用"消息能力。
- **流程**：

  1. 内部应用在 **HUB 系统**申请队列权限与消息类型 `tag`；
  2. 拿到队列和 `tag` 后，按标准向队列发送消息；
  3. 消息字段固定为：`msg_id`（消息 ID）、`tag`（消息类型）、`data`（消息体）；
  4. 第三方应用在**控制台**申请订阅，并把接收消息的 REST 接口绑定到订阅上；
  5. 第三方按约定格式返回结果（书中以"购买成功 / 失败"为例）。

> **SPI 网关 vs 消息网关**：都是内部调外部。SPI 是**同步调用接口**；消息网关是**异步消息 / 事件**。

## 三、支撑系统一览

| 系统 | 作用 | 记忆点 |
| --- | --- | --- |
| **服务市场** | 第三方应用开发者开发的应用的**售卖环境** | 对接完成后申请上架，用户即可购买 |
| **授权系统** | 用户获取系统**访问凭证**的入口 | 本书重点 |
| **控制台系统** | 第三方开发者申请、管理应用 | 开发者的"**个人工作台**" |
| **门户系统** | 介绍系统、提供对接文档 | 开发者**学习与查文档**的地方 |
| **HUB 系统** | 内部应用对接开放平台的主要系统 | 发布 API、定义 SPI、发布 MQ |
| **CMS 系统** | 内容管理系统 | 管理**门户系统**中的文章 |
| **MAN 系统** | 供开放平台**运营人员**使用 | 审核 HUB 内部用户的申请 + 平台管理 |
| **加解密系统** | 内外信息加解密 | 内部走 RPC，外部通过 API 网关 |
| **用户登录认证系统** | 用户登录认证 | **图 2-1 未画**：通常由专职部门开发管理，平台只需对接 |

> 关于"用户登录认证系统"：它一般由专职部门负责开发与管理，开放平台只做对接，因此图中没有画出来。这并不是强制标准——如果开放平台自己实现了登录认证模块，它应当出现在外部系统中。

## 四、把流程串起来

### 场景 A：第三方调用平台能力

```text
第三方应用
  │ ① 控制台创建应用、申请权限包
  ▼
控制台系统 ──▶ 授权系统 ──▶ 用户授权
  │                           │
  │ ② 拿到 token              │
  ▼                           ▼
HttpClient / SDK ───────▶ API 网关 ──校验 token──▶ 内部应用（RPC / REST）
                                                        │
                         ◀────────── 返回结果 ───────────┘
```

### 场景 B：平台反向调用第三方

```text
内部应用 ──▶ SPI 网关 ──指定 client_id──▶ 第三方应用（按 HUB 定义的协议实现 REST）
内部应用 ──▶ 消息网关 ──msg_id / tag / data──▶ 第三方应用（订阅队列，绑定 REST 接收）
```

## 五、API 网关（2.2）

> 第二节只说了 API 网关“是第三方调内部的入口”，这一节说它**怎么造**、**怎么鉴权**。

### 1. 它是什么、分几类

**API 网关是一种业务性的网关**，按应用场景分为 3 类：

| 类型 | 服务对象 | 说明 |
| --- | --- | --- |
| **OpenAPI 网关** | 第三方应用 | 通过 **REST** 方式把企业自身的数据和能力对外开放；**本书重点** |
| **微服务网关** | 内部服务 | 微服务集群的统一入口 |
| **API 服务管理平台** | 内部 API 治理 | 内部 API 的发布、管理、监控 |

> 书中只点了这三类的名字并主攻第一类；后两类的描述是按常见理解补的，只为便于区分。

### 2. 三种实现方案

| 方案 | 代表产品 | 特点 |
| --- | --- | --- |
| **Nginx + Lua + OpenResty** | Kong、Orange | 借 Nginx 的高性能，用 Lua 脚本做扩展 |
| **Netty** | 各公司自研 | Netty 只提供**多路复用 + 非阻塞**的 Socket 开发框架，选它就得**二次开发**出自己的网关 |
| **Java Servlet** | Zuul | 像写普通 Web 应用那样写网关，实现简单 |

**书中的经验：**

- 前两种是**异步非阻塞**方案，相比之下 Servlet 方案**并不高效**；
- 但 **Servlet 3.1 引入了异步非阻塞**，Servlet 方案因此也成了**简单可行**的选择；
- 本书的开放平台用的就是 **Java Servlet 3.1** 方案，并能充分利用其异步非阻塞特性。

### 3. 整体架构（图 2-2）

API 网关的整体架构如图 2-2 所示：**Nginx 层**负责限流与安全防护，**Servlet 层**负责业务编排，再向下按 REST / RPC 两条路访问内部应用。

![[图2-2API网关整体架构.excalidraw]]

*图 2-2 API 网关整体架构*

分层职责：

| 层 | 做什么 | 关键点 |
| --- | --- | --- |
| **Nginx 层** | 基础**限流**与**安全防护** | 基于公司提供的基础网络防护功能 + Nginx + Lua 脚本 |
| **Servlet 层** | 业务编排 | 使用 **Servlet 异步**，通过 **pipeline** 灵活组织业务 |
| **后端调用** | 访问内部应用 | REST 场景用 **HttpClient 4 异步调用**；RPC 场景用公司**自研异步调用框架**进一步提升吞吐量 |

```text
第三方请求
   │
   ▼
Nginx 层（限流 / 安全防护 + Lua 脚本）
   │
   ▼
Servlet 层（异步 + pipeline 编排业务，含鉴权）
   │
   ├── REST 场景 ──▶ HttpClient 4 异步 ──▶ 内部应用（REST）
   └── RPC  场景 ──▶ 自研异步框架      ──▶ 内部应用（RPC）
```

### 4. 网关与授权系统的关系（2.2.2）

从图 2-2 可以看到，网关里有一环是“**权限控制**”，也就是**鉴权**。

用户调用 API 网关时，一般会创建这样的请求（示例 2.1）：

```http
https://api.example.com/routerjson?access_token=##&client_id=##&method=##&v=##&sign=##&param_json=##&timestamp=##
```

*示例 2.1 API 网关请求*

> `##` 同样代表参数占位符（约定见 [[30-后端开发/80-接口与协议/10-OAuth2/02-OAuth 2 的四种授权模式|02-OAuth 2 的四种授权模式]] 开头的“阅读约定”）。

| 参数 | 含义 |
| --- | --- |
| `access_token` | 通过授权系统授权后得到的令牌，**即示例 1.6 中的 `access_token`**（见 02 篇“步骤 4：拿到授权信息”） |
| `client_id` | 第三方应用在开放平台注册完成后获取的唯一标识 |
| `method` | 本次请求要调用的方法 |
| `v` | 本次请求要调用方法的**版本** |
| `sign` | 对所有参数**排序**后，用摘要算法（如 MD5、SHA-1）生成的签名；服务端会验签 |
| `param_json` | 调用方法时传递的参数；一般**不出现在 URL** 中，而是放在**请求体**里，即以 POST 提交 |
| `timestamp` | 请求的时间戳；服务端会校验，**时间相差太大就拒绝调用** |

**鉴权流程：**

```text
API 网关收到请求
   │ ① 拿 access_token + client_id 请求授权系统（一般走内部 RPC 框架）
   ▼
授权系统：校验 access_token 是否合法、是否在有效期内 ……
   │ ② 通过 → 返回具体的授权信息
   ▼
API 网关：放行，继续执行本次调用
```

- 校验不通过 → 网关直接拒绝，请求**不会透传**到内部应用。
- 所以 `access_token` 在这里的作用很明确：**它是网关做权限控制的依据**，不是给第三方自己看的。

> 两道关卡别混：`access_token` 管“**有没有权限**”；`sign` + `timestamp` 管“**参数有没有被篡改、请求是不是重放**”。

## 六、控制台系统（2.3）

### 1. 定位

控制台系统是**第三方应用开发者的操作中心**——开发者在这里把应用“建起来、申请够、管到底”。

### 2. 六项核心功能（2.3.1）

| 功能 | 具体内容 | 记住这句 |
| --- | --- | --- |
| **应用基础信息** | 创建并管理 `client_id`、`client_secret`、回调地址、IP 地址白名单等 | 授权系统校验时**要用这些数据** |
| **申请权限包** | 权限包对应**一组 API 的调用权限**；一个权限包会按需求划分到多个 **scope** 权限中 | scope 之间**可以有权限重叠** |
| **申请流量包** | 一般**绑定在具体 API** 上；初始只够最基本需求，不够就提交申请提额；有多种规格，**部分可能收费** | 权限管“能不能调”，流量管“**能调多少**” |
| **下载 SDK** | 平台提供的 SDK 封装底层授权 + API 调用逻辑 | 降低第三方接入成本 |
| **生命周期管理** | 上线、下线、删除 | 应用的状态开关 |
| **操作中心扩展** | 消息订阅、SPI 注册 | 分别对接**消息网关**与 **SPI 网关** |

### 3. 控制台与授权系统的关系（2.3.2）

三条关系：

1. **参数校验的数据源**
   授权系统授权时必须验证请求参数的正确性——`client_id`、`client_secret`、`redirect_url` 等是否有效。这些信息都**存在控制台系统**里。

2. **强制 IP 白名单**
   为保护开放平台安全，授权系统一般**强制要求**第三方在控制台配置 **IP 地址白名单**；授权时会校验请求的客户端是否在白名单中。

3. **Scope 取交集**

```text
第三方请求的 scope 列表
        ∩
控制台中该应用已配置的权限包（对应的一组 scope）
        │
        ▼
展示给用户的授权列表（明确告知：会把哪些权限授给这个应用）
        │
        ▼
用户同意 → 第三方获得 API 操作能力 + 用户信息获取能力
```

> 为什么要取交集：应用**申请**的范围未必等于平台**批准**的范围。取交集才能保证“展示给用户、实际授出去”的权限，不超过已审批的权限包。

## 七、服务市场（2.4）

### 1. 两类第三方应用

| 类型 | 谁在用 | 是否售卖 | 授权时要不要看购买 |
| --- | --- | --- | --- |
| **自研型应用** | 只供自身账号使用 | 否 | 不用 |
| **售卖型应用** | 其他用户购买后使用 | 是，**定价后发布到服务市场** | **要**，见下 |

服务市场就是**售卖场所**：开发者把自己基于开放平台做出的应用上架，开放平台的用户按需购买。

### 2. 售卖型应用的特殊之处：token 有效期

`access_token` 本身有**过期时间**，而且**没有具体标准**——有的几小时，有的长达几天。售卖型应用还多一层约束：**用户买了多久**。

```text
授权系统准备生成 access_token
   │ ① 判断：是不是售卖型应用？
   │ ② 是 → 调用服务市场，取当前用户对该应用的购买有效期
   ▼
没买过 ─────────────▶ 直接拒绝授权
已购买且在有效期内 ──▶ access_token 有效期 = min(系统默认有效期, 剩余购买有效期)
```

一句话：**取两者中较小的那个**——平台默认给多久，用户就只剩多久，谁小听谁的；没买过就是没资格。

### 3. 售卖型应用的两种授权方式

| 方式 | 授权发生在哪 | 特点 |
| --- | --- | --- |
| **第三方应用引导授权** | 第三方应用内 | 常规 OAuth 流程，用户要走一遍授权页面 |
| **插件化授权** | **服务市场内** | 服务市场**已持有用户登录状态**，用户直接点“授权”同意即可，**无须再次登录** |

> 插件化授权的省事之处只在“**免登录**”：用户本来就在服务市场里登录着，不用为了一次授权再登一遍。

## 八、易混点小抄

- **API 网关 vs SPI 网关**：方向相反。API 是"外部调内部"，SPI 是"内部调外部"。
- **SPI 网关 vs 消息网关**：都用于内部调外部；前者同步调接口，后者异步发消息。
- **HUB 系统是内部应用的统一入口**：发布 API、定义 SPI、发布 MQ 都在这里。
- **控制台 vs MAN**：控制台给**第三方开发者**用；MAN 给**平台运营人员**用。
- **门户 vs CMS**：门户是给人看的文档站；CMS 是管理门户文章的后台。
- **加解密系统是"内外通吃"**：内部走 RPC，外部通过 API 网关暴露。
- **图里没有登录认证系统 ≠ 不需要**：它通常由专职部门提供，平台负责对接。
- **“三类网关” ≠ “三座网关”**：OpenAPI / 微服务 / API 服务管理平台是按**应用场景**分的；API / SPI / 消息网关是按**调用方向**分的。
- **Nginx 层管“进得来”，Servlet 层管“怎么走”**：限流与安全防护在 Nginx；业务编排靠 Servlet 异步 + pipeline。
- **`access_token` 和 `sign` 是两道关卡**：前者管“有没有权限”，后者（连同 `timestamp`）管“参数有没有被改、请求是不是重放”。
- **权限包 ⊃ scope**：一个权限包会拆到多个 scope，scope 之间还能重叠；授权时展示的是“**请求的 scope ∩ 已批准的权限包**”。
- **权限 vs 流量**：权限包决定**能不能调**，流量包决定**能调多少**。
- **售卖型应用的 token 有效期取较小值**：`min(系统默认有效期, 剩余购买有效期)`；**没买过直接拒绝**。
- **自研型 ≠ 售卖型**：自研型只给自己账号用、不售卖；售卖型要上架服务市场，授权时必须校验购买有效期。

## 九、专有名词与缩写

| 缩写 / 术语          | 英文全称                                 | 中文含义                | 在本笔记中的作用                           |
| ---------------- | ------------------------------------ | ------------------- | ---------------------------------- |
| **API**          | Application Programming Interface    | 应用程序编程接口            | 系统对外提供的可调用接口；这里指开放平台开放给第三方的接口      |
| **SPI**          | Service Provider Interface           | 服务提供者接口             | 与 API 方向相反：内部定义协议标准，由第三方实现接口，供内部调用 |
| **SDK**          | Software Development Kit             | 软件开发工具包             | 平台提供的客户端工具包，封装调用 API 的鉴权、请求等细节     |
| **RPC**          | Remote Procedure Call                | 远程过程调用              | 像调本地方法一样调用远程服务；内部应用之间常用            |
| **REST**         | Representational State Transfer      | 表述性状态转移             | 基于 HTTP 的资源式接口风格                   |
| **MQ**           | Message Queue                        | 消息队列                | 异步消息中间件；消息网关借此传递消息                 |

### 2.2–2.4 新增术语

| 缩写 / 术语 | 英文全称 | 中文含义 | 在本笔记中的作用 |
| --- | --- | --- | --- |
| **OpenAPI** | Open API | 开放 API | OpenAPI 网关对外开放的那一类接口 |
| **Nginx** | — | 高性能 Web / 反向代理服务器 | API 网关的前置层，承担限流与安全防护 |
| **Lua** | — | 轻量级脚本语言 | 在 Nginx 中编写扩展逻辑 |
| **OpenResty** | — | 基于 Nginx + Lua 的 Web 平台 | “Nginx + Lua”方案的常见底座 |
| **Kong / Orange** | — | 开源网关产品 | Nginx + Lua + OpenResty 方案的代表 |
| **Netty** | — | 异步事件驱动的网络框架 | 只提供多路复用与非阻塞 Socket 能力，做网关需二次开发 |
| **Socket** | — | 套接字 | 网络通信的编程接口 |
| **多路复用 / 非阻塞** | Multiplexing / Non-blocking | — | 一个线程管多条连接、等待 IO 时不阻塞，是高吞吐的基础 |
| **Servlet** | Java Servlet | Java Web 组件规范 | 处理 HTTP 请求；3.1 起支持异步非阻塞 |
| **Zuul** | — | Netflix 开源的 API 网关 | Java Servlet 方案的代表 |
| **pipeline** | — | 流水线 / 责任链式处理 | Servlet 层用它灵活组织业务 |
| **sign** | Signature | 签名 | 参数排序后经摘要算法生成，服务端验签防篡改 |
| **摘要算法** | Digest / Hash | 哈希算法 | 把任意长度输入压成定长摘要 |
| **MD5 / SHA-1** | Message-Digest Algorithm 5 / Secure Hash Algorithm 1 | 消息摘要算法 | 用于生成 `sign`；做参数签名仍常见 |
| **scope** | — | 权限范围 | 授权请求中声明的权限列表，与权限包取**交集** |
| **IP 白名单** | IP Whitelist | IP 地址白名单 | 只允许名单内的来源调用，授权系统会强制校验 |
| **流量包** | — | 调用量配额 | 绑定在具体 API 上；可申请提额，部分规格收费 |
| **自研型 / 售卖型应用** | — | — | 自研型只供自身账号用；售卖型定价上架服务市场 |

补充概念：

- **权限包**：把一组 API 权限打包，第三方应用申请、平台审核后获得。一个权限包会按需求划分到多个 **scope** 中（scope 之间可以重叠），授权时与请求的 scope 列表**取交集**。
- **微服务网关 / API 服务管理平台**：与 **OpenAPI 网关**并列的另两类网关，服务对象分别是内部微服务、内部 API 治理（书中只点名，未展开）。
- **Web / App**：Web 指浏览器端网页应用；App 指移动端应用。
- **开放平台 / 第三方应用**：见 [[30-后端开发/80-接口与协议/10-OAuth2/01-OAuth 2 的定义与核心角色|01-OAuth 2 的定义与核心角色]]。

> 易混：**API** 是“别人调我”（对外提供），**SPI** 是“我调别人”（对外要求实现）。在开放平台里，API 网关负责前者的入口，SPI 网关负责后者的出口。
